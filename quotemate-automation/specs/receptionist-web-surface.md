# Spec: Web surface for every deployed SMS AI Receptionist

## Goal

Each of the six deployed services (electrical, plumbing, roofing, painting,
solar receptionists + the Front Desk) gets a browser-facing website served by
its own NestJS app: home page, documentation, Swagger explorer, a live chat
sandbox, an API-keys page, and login/logout protecting the sensitive pages.
One shared design system across all six.

## Decisions (locked)

1. **Swagger**: keep the existing `/api/docs` Swagger UI; add an
   `/api-explorer` page that wraps it in the site chrome via a same-origin
   iframe. No custom API explorer.
2. **API keys**: display-only. The keys page shows the service's configured
   keys (masked, reveal + copy) to a logged-in operator, with rotation
   documented as "change the Railway variable". No key-issuing database.
3. **Sandbox**: calls the real pipeline via each service's existing simulate
   channel, gated behind login, with a prominent live-fire warning and the
   From-number defaulting to a test number. Receptionists: self-POST to their
   own `/api/receptionist/simulate` with `SIM_API_KEY` server-side, then poll
   Supabase `sms_messages` for the outbound reply. Front Desk: call its own
   `/api/front-desk/message` (returns the reply synchronously).
4. **Front Desk included**: yes — same pages, router-flavoured content.

## Pages (every service)

| Path | Auth | Content |
|---|---|---|
| `/` | public | Hero (service name, trade chip, tagline, live status pill), what-it-is, capabilities grid, **three Mermaid diagrams** (per-service message flow; fleet/system architecture group diagram; internal module design), test-it cards, endpoints table, footer linking all six services |
| `/documentation` | public | Full reference: how it works, endpoint reference w/ example request+response, authentication model, env-var reference (names only), testing guide (Swagger steps, sandbox steps, Twilio wiring) |
| `/api-explorer` | public | Site chrome + iframe of `/api/docs` |
| `/sandbox` | **login** | Chat UI: message list, input, From/To fields (From defaults to test number), status line, live-fire warning banner |
| `/keys` | **login** | Masked keys with reveal/copy, curl examples, webhook URL, rotation instructions |
| `/login` | public | Password form; error state; redirects to `next` |

## Auth

- Single operator password: `WEB_ADMIN_PASSWORD` env var (optional — unset ⇒
  login disabled, gated pages explain how to enable; boot unaffected).
- Session: HMAC-signed cookie `qm_web` = `<exp>.<hmac>`, secret =
  `WEB_SESSION_SECRET` or derived `sha256(WEB_ADMIN_PASSWORD + service)`,
  TTL 24h, HttpOnly, SameSite=Lax, Secure behind HTTPS.
- `POST /web/login` (form) sets cookie; `POST /web/logout` clears it.
- Guard protects `/sandbox`, `/keys`, `POST /web/api/sandbox/message`,
  `GET /web/api/keys`. Pages redirect to `/login?next=…`; APIs return 401.
- Password compare: constant-time. Session logic has a runnable
  `session.check.ts` (assert-based, repo's existing `*.check.ts` pattern),
  written before the implementation is considered done.

## Design system (identical across services)

- Tokens: canvas `#16120F`, panel `#1C1712`, line `#2B241D`, ink `#F4EFE7`,
  muted `#9C917F`, accent `#FFC400`, per-service trade tint
  (electrical `#FFD34D`, plumbing `#6EC1FF`, roofing `#FF7A59`,
  painting `#C9A7FF`, solar `#7BE495`, front desk `#FFC400`).
- Manrope (display/body) + JetBrains Mono (labels, code) with system
  fallbacks; uppercase mono kickers; square corners; 1px hairline borders and
  lit top-edges, no drop shadows; zero emoji; Australian English.
- Shared nav (service name + trade chip · Home / Documentation / API /
  Sandbox / Keys · Login/Logout) and shared footer (all six services).
- Mermaid via CDN, themed to the tokens.

## Implementation shape

- Receptionists: pages generated by `scripts/export-receptionist.mjs`
  (templates in the generator, per-trade content in `TRADES`), so re-syncs
  preserve the surface. New files under `src/web/`:
  `design.ts`, `content.ts`, `session.ts`, `session.check.ts`,
  `auth.guard.ts` (may live in session.ts), `web.controller.ts`,
  `sandbox.service.ts`, `web.module.ts`; `WebModule` registered in
  `app.module.ts`.
- Front Desk: same files written directly in its repo, content adapted to
  the router role; replaces its old root HTML page.
- `.env.example`: new "Web surface" group (`WEB_ADMIN_PASSWORD`,
  `WEB_SESSION_SECRET`).

## Deployment

- `WEB_ADMIN_PASSWORD` + `WEB_SESSION_SECRET` generated (one value across
  the fleet, stored in each repo's `.env`, never printed to chat), pushed to
  all six Railway services, redeployed, and live-verified.

## Definition of done (review checklist)

1. All six repos build (`tsc --noEmit` 0 errors, `npm run build` OK).
2. `session.check.ts` passes in a receptionist repo and the front desk.
3. Booted locally: `/`, `/documentation`, `/api-explorer`, `/login` return
   200; `/sandbox` and `/keys` redirect (302) to `/login` when logged out;
   wrong password re-renders login with error; correct password → cookie →
   `/sandbox` and `/keys` return 200; `/web/logout` clears access.
4. Home page HTML contains all three Mermaid diagram definitions and the
   fleet footer links.
5. `/api/docs` (Swagger) still serves; `/api-explorer` iframes it.
6. Per-trade content differs across services (tagline + flow diagram).
7. Existing API routes unaffected (`/api/health`, `/api/health/deep`,
   `/api/sms/inbound`, simulate/message routes).
8. All six deployed on Railway: every page live, gated pages redirect, and
   the two web env vars set on every service.
9. No secret value in any committed file or in chat output.
